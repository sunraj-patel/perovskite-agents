Reviewer-facing benchmark for the manuscript system (Orchestrator + five prompted
agents with progress contracts, `codebase/perovagents/`). It compares, **per
model backbone**, two conditions that share the same scientific tools, data,
budgets, questions and scorer:

| condition | what runs |
|---|---|
| `direct` | the existing `DirectBaseline` (`benchmarks/harness.py`): one LLM, the tool catalogue, no orchestrator / agent briefings / progress contracts / verifier |
| `perovagents` | the existing `Orchestrator` over `pdb`, `literature`, `ml`, `scaps`, `design` agents (`perovagents/agent.py`, `team.py`, `progress.py`) |

Nothing in `perovagents/` or the original `benchmarks/*.py` was modified. Everything
new lives in `benchmarks/agentic_paper/`.

## Questions

Q01-Q20 are the original frozen questions (IDs, text, categories and required
outputs unchanged; their pilot results in `results/cross_llm/` are untouched).
Q21-Q45 were added so that every category has **eight** questions in the main set:

| category | main questions | notes |
|---|---|---|
| Experimental database | Q01-Q04, Q21-Q24 | SQL references on the SQLite mirror (43,398 devices) |
| Literature retrieval | Q05-Q08, Q25-Q28 | 22-paper collection; DOI + number checks; numbers asserted in paper text at build time |
| ML prediction / explanation / what-if | Q09-Q12, Q29-Q32 | frozen CatBoost artefacts (determinism checked) |
| SCAPS sensitivity (precomputed) | Q33-Q40 | six stored sweeps of the n-i-p reference cell; **no live solver** |
| Multi-tool | Q17-Q19, Q41-Q45 | >= 2 capabilities each |

Five questions need the live solver (Q13, Q14, Q15, Q16, Q20). They are frozen
and kept (`set: live_scaps_case_study`) but excluded from the main set. Five main
questions are *insufficient-evidence* items whose correct response is to say so
(Q24, Q28, Q32, Q40 and the second half of Q45). Q17 and Q19 are open-ended and
only have structural checks; they are flagged `manual_review` in the scored files.

Each question stores: exact query, required outputs, acceptable reference plans
(required + optional tool actions, alternatives allowed), sequencing constraints,
dependencies, deterministic checks with tolerances and units, and provenance.

## Metrics (scorer.py)

* **Completion**: the episode ended with an answer, did not declare failure (answer-type questions), and every mandatory output is *present* (a number in a loose band around the reference, the DOI string, the required terms, or an explicit statement of insufficient evidence). The model saying it is done is not evidence.
* **Correctness (binary)**: completion and every mandatory check passes its value rule (tolerance, units, DOI cited as *supporting* evidence rather than rejected, names recalled, no forbidden fabricated claim). `correct` implies `completed`. **Partial credit** = fraction of all checks passed.
* **Tool-selection P/R/F1**: set of canonical tool actions used vs the best-matching acceptable plan (`db.query`, `lit.search`, `lit.read`, `ml.*`, `scaps.sweep`, `scaps.describe`, `design.layout`...); calculator calls excluded. Valid alternative plans are accepted; missing dependencies and sequencing constraints are recorded separately (`dependencies_satisfied`, `sequencing_satisfied`).
* **Efficiency**: wall-clock, model calls, tool calls, retries (repeated identical calls + empty-reply retries), timeouts, rate-limit and provider-error events, real token usage when every call reported it. Gemini reports usage per call; the OpenCode route reports OpenCode's own accounting, which includes OpenCode's agent prompt.
* **Failure analysis**: multi-label (`incorrect_tool_selection`, `repeated_actions`, `tool_errors`, `incomplete_answer`, `unsupported_claim`, `incorrect_value`, `incorrect_citation`, `budget_exhaustion`, `infrastructure_failure`) with a one-line evidence string drawn from the trace, and one primary label by fixed priority.

Correct reporting of a tool output is not scientific validity: references come from
the same data/tools the agents use, so the benchmark measures faithful and complete
use of the tools, not whether a prediction or simulation is physically right.

## Statistics

The question is the unit. Repetitions of a (backbone, condition, question) cell are
averaged first. Intervals are 95% percentile intervals from a **paired bootstrap that
resamples question IDs** (B = 10,000, fixed seed); both conditions and all metrics of a
backbone use the same resampled questions, so paired differences keep their
covariance. Category intervals resample the (8) questions of that category and are
wide by construction. Infrastructure failures are excluded from agent-performance
denominators and reported separately.

## Model access (free only)

* **Gemini**: `gemini-3.8-flash` through the google-genai SDK with the free-tier key pool read from `~/keys.md` (rotated, invalid keys skipped). Keys are never logged or stored; provider events refer to pool slot numbers.
* **DeepSeek / MiniMax**: `opencode/deepseek-v4.1-flash-free` and `opencode/minimax-m3.1-flash-free` through `opencode serve` (start with `./start_opencode_server.sh`). The free-tier gateway only accepts requests that still carry OpenCode's tool list, so tools cannot be removed; the script instead runs the server in an empty sandbox git root with deny-by-default file tools, no shell/edit/web, and temperature 0 (verified: file reads outside the sandbox, including these reference answers, are refused).
* No backbone ever falls back to another model, provider or a deterministic responder. A call that cannot be served after bounded retries aborts the episode, which is recorded as `infra_failed` and re-queued on resume. After 4 consecutive infrastructure failures a backbone stops; the other backbones continue.
* The local Ollama model (`qwen3.5:35b`) was not used: a 35B model, server not running, no authorisation to load it.

## Running

```bash
cd codebase                                   # repository root
python -m benchmarks.agentic_paper.build_reference     # only if data changed
python -m benchmarks.agentic_paper.build_questions
python -m benchmarks.agentic_paper.selfcheck           # static checks + scorer controls
python -m benchmarks.agentic_paper.freeze              # writes FREEZE.json
./benchmarks/agentic_paper/start_opencode_server.sh &  # for the OpenCode routes
python -m benchmarks.agentic_paper.run --stage smoke   # 3 questions x backbones x conditions
python -m benchmarks.agentic_paper.run --stage pass --reps 3 --workers 4    # resumable
python -m benchmarks.agentic_paper.run --status
python -m benchmarks.agentic_paper.refresh             # score + tables + figures
python -m benchmarks.agentic_paper.make_report         # regenerate BENCHMARK_REPORT.md
```

Large external data (SQLite mirror, paper collection, SCAPS sweeps) are located via
`PEROVAGENTS_PDB_SQLITE`, `PEROVAGENTS_CORPUS_DIR`, `PEROVAGENTS_SCAPS_DIR` (defaults in
`paths.py`); their SHA-256 values are in `FREEZE.json`. `run.py` refuses a main run
if the frozen files changed.

## Keeping the manuscript figures up to date

`refresh.py` rewrites the same four files each time, with fixed size, axes, colours
and backbone slots (taken from `config/models.json`, so a backbone without results
shows "no data yet" instead of changing the layout):

```
figures/fig1_overall_comparison.pdf|png        completion / correctness / tool-F1
figures/fig2_category_performance.pdf|png      completion + correctness by category
```

An "interim: x of y episodes" stamp is drawn until the planned episodes are all
scored; `python -m benchmarks.agentic_paper.figures --final` removes it.
`python -m benchmarks.agentic_paper.refresh --export-to <dir>` copies the four files
to a manuscript figure directory (never run automatically). In LaTeX include them
with fixed names, e.g. `\includegraphics[width=\textwidth]{fig1_overall_comparison}`;
re-running `refresh` and re-copying is all that is needed as runs accumulate.
Numbers behind each figure: `figures/fig1_overall_data.csv`, `figures/fig2_category_data.csv`.

## Known constraints

See `BENCHMARK_REPORT.md` ("Limitations"). Key ones: budgets are identical in total
(12 tool calls / 12 model turns / 1200 s) but PerovAgents additionally allows 12 turns
per sub-agent and 5 orchestrator rounds; the OpenCode route is an agent wrapper rather
than a bare completion (hidden internal steps, its own prompt); references are built
from the tools under test; the literature gold has one verified paper for Q05-Q08;
Q17/Q19 need manual review; wall-clock includes provider latency and rate-limit waits
and runs share a machine.
